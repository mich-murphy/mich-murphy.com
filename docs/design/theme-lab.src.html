After reading posts from both Graham Christensen and Elis Hirwing about the idea of impermanence in NixOS I decided to try setting it up on my homelab. The basic idea is that we configure the system to use a temporary file system, where everything is wiped after a reboot, unless specified otherwise.

One of the major benefits of this kind of setup is that it forces you to properly declare the configuration, as everything will break after a reboot otherwise.

Initial Setup

For the initial installation of NixOS I followed Elis' walk through (linked above) and configured root using a temporary file system. Once this was complete I added the nix community tool impermanence to /etc/nixos/configuration.nix to allow for a declarative configuration going forward.

Configuring Persistence

With the above complete I was able to configure directories I needed to persist from within /etc/nixos/configuration.nix.

Initially I ran into issues configuring Tailscale as I would be logged out after each reboot, I found persisting /var/lib fixed the issue as it ensures the Tailscale state, located at /var/lib/tailscale/tailscale.state, is always available.

Managing Users

You may have noticed in the configuration above I also persist /users/admin, this allows me to store a hashed password for the user inside of the directory, which is read from within /etc/nixos/configuration.nix.

Whilst migrating my homelab from Ubuntu to Nixos I came across the need to schedule a cron job, which I had setup to sync my media collection from a remote server. After doing a bit of research I discovered that rather than using a cron job, the preferred method is to create a systemd service and schedule it using a systemd timer. The major benefits of doing so are:

  1. Jobs can be isolated to specific users
  2. Environment variables and paths can be explicitly declared
  3. Logging is easily viewed by systemctl start example followed by journalctl --unit=example
  4. Timers let you know when the service will next run systemctl status example.timer

How search works

The archive is small: 17 posts, 1,127 lines. At that size the fastest and most exact search is the plainest one. The index page loads the lines once, when the box first gets focus, and checks every line of every post on each keystroke. That takes under a tenth of a millisecond (measured over the real index), so results keep up with typing and nothing needs a server.

  1. accurate

    Every word must match. Words match from the start of a word, so imperm finds impermanence and rsa finds ssh_host_rsa_key, but sy skips "easy". Quotes keep a phrase together, and a single letter waits for a second one. Posts rank by where the words turn up: title, then tag, heading, prose, code, and then by how often. Ties go to the newer post. There's no fuzzy matching: a search finds what you typed, the way grep does. It searches what a reader sees, so a link's URL doesn't match.

  2. filters

    Words go in the box. Under it, two menus narrow the list: tag: all and year: all. A menu opens over the posts with every tag or year and the number of posts each would leave. One that would leave none is switched off. Picking one replaces the one before it. A set menu shows its value inverted, with a × beside it that clears it, and the list's label reads Posts · 7 of 17. A tag or year typed in full, then a space, moves out of the box into its menu, so typing #nixos backup still works. A tag link on a post opens /#nixos with the tag menu set. A search updates the address as /?q=…, so you can share it.

  3. keys

    / jumps to the box, which is honest here because this page has the script. Esc closes an open menu, then clears the words, then the filters. ↓ moves into the results, and Enter opens the top post. The match count is announced to screen readers as it changes.

  4. no script

    The box stays hidden, the frame is labelled Filter, and every post is listed. The two menus still open, because they're <details>. Their entries are links like /#nixos that filter the list through :target, one filter at a time, and all or × brings every post back. Without the script nothing closes a menu after a pick, so there the open list sits under the menus and pushes the posts down instead of covering them. The "index without a script" switch shows this.

  5. cost

    The index page carries about __GREP_JS_KB__ KB of script, and its footer says so. It also fetches the 29 KB index on first focus. Every other page stays at 0 B js.

  6. libraries

    I measured these, gzipped: FlexSearch (light) 2.8 KB, MiniSearch 6.0 KB, Lunr 8.2 KB, Fuse.js 8.9 KB. Pagefind needed about 150 KB for the first query. They add typo tolerance and word stemming, but none of them returns the line that matched, and for 17 posts they cost more than they give. MiniSearch is the one to revisit if the archive reaches a few hundred posts or typos start to matter.

How the status line works

Each post has a strip pinned to the bottom of the window, drawn like the ruled header: 12px text on the page colour under a 2px rule. The left side shows the post title until a heading scrolls past, then the current section as h2 › h3, marked with the 7px square. The right side shows how far through the post you are and the minutes left, counting down from the post's reading time. The rule along its top fills from left to right as you read. Hovering the strip, or tabbing into it, opens the Contents box upward with every heading, and clicking an entry jumps to it. It needs no margin, so it works at every width, phones included, and no separate narrow-screen contents is needed.

None of it uses JavaScript. The section name is a stack of anchor links, one per heading, in a list with scroll-target-group. Only the one matching :target-current is visible. That works in Chrome and Edge 140 and later, and other browsers show the post title. The rule, the percentage and the minutes left are scroll-driven animations (animation-timeline: scroll()) on a registered integer shown through a CSS counter. They work in Chrome and Edge 115+ and Safari 26+. Safari needs calc() around the animated integer, or the counter reads 0. Firefox still has scroll-driven animations behind a flag, so there they're hidden inside @supports and the strip shows only the title and the Contents box. The Contents box is hidden with opacity rather than visibility, so its links stay in the tab order and :focus-within opens it. On the site the strip is position:fixed. In this preview it's sticky inside the frame.

This lab adds a few lines of script so the section name and the progress show in any browser. The site ships neither. The ticks rail from rev 8 is still under “Every switch” as “contents rail”.

Colophon

The source file's path is cut into the border where a title would go. Below it is one keyed list, with muted keys in a column of their own and values in full ink: created, updated, and commit. The commit row is the hash, in the accent and linked, with history at the right end. On phones history drops below the row. Under a dotted rule, the same keyed style gives what the post is made of: words 687 · code blocks 5 · Bash 4 · YAML 1, using the language names from the code title bars. It's the only dithered box on a post page, and its frame lines up with the text column. Under it, Older and Newer name the neighbouring posts by their source files: ‹ systemd-services-and-timers-nixos.md at the left end of the column and nixos-tmpfs-installation.md › at the right. A post at either end of the history has only one.

The dates and commits shown here are the posts' real history from before the move to Hugo. The build backfills them, so the migration commit doesn't show as a change on every post. Rev 10 showed the commit's message after the hash. It's gone, because a message like “edits to latest post” told readers nothing.

Social card

Generated at build time from the page's title and date, in the same parts as the site: the ruled header with the shadow stamp, the framed card with the shade dither, and the title in 0xProto Bold. Hugo draws it with its image functions using the OFL-licensed 0xProto file, plus a small PNG tile for the dither. Readers never download it. Only link previews fetch it.

The design

  • 0xProto Regular and Bold (OFL, self-hosted, subset to about 28 KB each), dark first with the tuned palette, light following the OS setting. Five sizes: 12, 13.5, 15, 19 and 24px.
  • Ruled header with the shadow stamp at 24px, which is also the favicon. The name is in capitals, the nav reads as written, and a 7px square marks the current section.
  • Home: a short intro, the Search box, then the Posts card (title and date, the page's one dithered box) with every post. The card filters as you type, and two menus under the box narrow it to a tag or a year. That replaces the tag pages.
  • About: the bio, the Projects card, and "This site". GitHub is in every footer. Feeds: the Subscribe box, and the blogroll from a file you edit.
  • Posts: a single column, with the status line pinned to the bottom of the window. It shows the current section, how far through you are and the minutes left, and opens the contents on hover or focus. Title, then date, reading time and tags. Headings stand out through contrast and weight: h2 at 19px, h3 bold, body text slightly dimmed.
  • Code: a title bar when the block has a file path, a label in the border when it doesn't. No line numbers, two-tone syntax, and a soft edge where lines run on.
  • Callouts as framed boxes from > [!NOTE]. Square bullets and list numbers in the frame colour.
  • The path colophon at the end of each post, as one keyed list: created, updated, and the commit hash with a history link. Under a dotted rule, the words, code blocks and languages. It's the page's one dithered box. Older and Newer follow it, named by their source files.
  • Tags, a tag's page, 404, About and Feeds are built from the same parts: the Posts card, keyed boxes cut from the colophon, and the post head. Each page still has exactly one dithered box.
  • Footer: build hash, page weight written by CI, 0 B js, and atom.xml linking to the feed file.
  • Mermaid rendered to SVG at build time. Social cards generated at build time. A print stylesheet.
  • No JavaScript, except the index's search, whose footer says how much it carries. HTML and CSS under 14 KB compressed per page. The largest post today is about 4 KB of that.
